## 为什么要把 AI 编码放进流水线

过去一年，多数团队使用 AI 编码助手的方式仍然是「同步结对」：工程师打开 IDE 或终端，和模型一问一答，盯着它改代码。这种模式提升了个人效率，但没有改变团队的协作结构，人依然是瓶颈，AI 的产出依然要靠人实时看守。

异步流水线换了一个思路：**把 AI 当成一个只接受 Issue、只交付 PR 的协作者**。需求方在 Issue 里写清楚要什么，打上标签或在评论里 @ 一下，流水线在云端拉起 Agent，改代码或写文章，跑 lint 和构建，推送分支并给出 PR；部署平台为 PR 生成预览地址；人只在两个节点介入，一是写需求，二是审 PR。

本文以本站（Next.js 静态导出 + Netlify 托管）为例，讨论三件事：调用通道为什么必须选对；闭环的每一环如何设计；以及我们实际踩过的坑。

## 一、先选对通道：消费级账号为什么不适合跑在云上

很多人第一次尝试时，会把自己的个人订阅账号（例如 Claude Pro / Max 的登录态）直接搬到 CI 或云服务器上。短期内能跑通，但很容易遇到登录失效、请求被限流，甚至账号被要求重新验证。原因并不神秘，而是消费级账号的风控模型和服务器场景天然冲突。

### 风控看的是「像不像一个人」

消费级产品的风控假设是「一个自然人，在少数几台个人设备上交互使用」。在云服务器上运行时，几乎每个信号都和这个假设相反：

- **出口 IP**：GitHub Actions 的 hosted runner 和主流云厂商的 IP 段属于数据中心地址，同一段 IP 背后可能有成千上万个租户。这类地址在任何风控体系里都是高风险来源。
- **地理位置跳变**：工程师白天在本地登录，夜里 CI 从另一个大洲的机房发请求，同一账号短时间内出现在多个地理位置，这是典型的账号共享或盗用特征。
- **行为模式**：自动化任务没有输入间隔、没有阅读停顿，请求在固定时刻成批出现，并发度也可能远超个人使用。
- **凭证形态**：个人账号的 OAuth 登录态本来就是为交互式客户端设计的，需要定期刷新。把它导出成 Secret 塞进 CI，本身就脱离了它的设计用途，也往往与消费级服务条款中关于自动化和共享使用的约定相抵触。

所以这不是「运气不好被误伤」，而是用法与产品定位错配。即便某段时间没出问题，它也是一个不可控的单点：账号一旦被限制，整条流水线和你的个人工作环境会同时停摆。

### 企业 API 与云托管通道的差异

API Key 和云托管通道（如 Amazon Bedrock、Google Vertex AI 上的 Claude）从一开始就是为程序化调用设计的，它们的契约完全不同：

- **身份是服务，不是人**：API Key 绑定的是组织和工作区，鉴权不依赖登录态，不需要人机验证，也不会因为 IP 来自机房而被判定异常。
- **限额是显式的**：速率限制和用量上限以文档化的 Tier 呈现，超限返回明确的 429 和重试头，而不是模糊的封禁。流水线可以据此做退避重试。
- **计费和审计可归属**：按 Token 计费，能按工作区或项目拆分成本；企业云通道还可以复用已有的 IAM、VPC、日志审计和数据驻留策略，这对需要过合规的团队往往是决定性因素。
- **故障隔离**：CI 用的 Key 和个人使用彻底分开，可以单独轮换、单独吊销，泄露时的影响范围可控。

落到架构决策上，结论很简单：**凡是无人值守的场景，一律走 API 或云托管通道**。个人订阅留给本地交互使用。如果团队已经在某家云上有合同和合规体系，优先选该云的模型托管服务；如果追求最快接入新模型，直接用官方 API。两者在 Claude Code Action 中都只是配置差异。

## 二、拆解闭环：从 Issue 到上线的五个环节

完整的闭环可以拆成五个环节，每个环节都有明确的输入、输出和负责方。

1. **需求入口（人）**：在 Issue 中写清楚目标、约束和验收标准，打上约定标签（本站使用 `ai-fix` 和 `ai-article`），或在评论里 @claude。
2. **触发与鉴权（GitHub Actions）**：工作流监听 `issues.labeled` 和 `issue_comment.created` 事件，先校验触发者身份，再拉起 Agent。
3. **执行与自检（Claude Agent）**：Agent 读取仓库中的 `CLAUDE.md` 规范，在独立分支上修改代码或撰写文章，执行 lint 和构建，全部通过后提交并推送。
4. **预览与评审（Netlify + 人）**：PR 创建后，Netlify 自动构建 Deploy Preview，评审者直接打开预览地址验收，而不只是读 diff。
5. **合并与发布（人 + Netlify）**：评审通过后 Merge 到 `main`，Netlify 触发生产构建，几分钟后上线。

这里有两个设计原则值得强调。

**第一，人只出现在入口和出口。** 中间三个环节全部自动化，但 Merge 权永远在人手里。Agent 的权限边界是「能推分支、能开 PR」，不能直接改 `main`，也不能修改 `.github/workflows` 目录。这条边界决定了最坏情况下的损失只是一个被关掉的 PR。

**第二，规范写进仓库，而不是写进 Prompt。** 本站在根目录的 `CLAUDE.md` 中约定了文章的 Frontmatter 字段、文件命名、MDX 防错规则、提交前必须通过的命令和分支规范。Agent 每次执行都会读取这份文件。这样做的好处是规范可以被 Code Review、可以版本化，任何人改了规范，下一次任务自动生效，不依赖某个人记得在 Prompt 里加一句话。

### 触发层的最小配置

下面是本站实际使用的工作流核心部分：

```yaml
on:
  issues:
    types: [labeled]
  issue_comment:
    types: [created]

permissions:
  contents: write
  pull-requests: write
  issues: write
  id-token: write

jobs:
  auto-fix:
    if: |
      (github.event_name == 'issues' &&
        (github.event.label.name == 'ai-fix' || github.event.label.name == 'ai-article') &&
        github.actor == 'tristanbao') ||
      (github.event_name == 'issue_comment' &&
        contains(github.event.comment.body, '@claude') &&
        github.actor == 'tristanbao')
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
        env:
          ANTHROPIC_BASE_URL: ${{ secrets.ANTHROPIC_BASE_URL }}
```

几个要点：

- **触发者身份校验是安全底线。** `if` 条件中的 `github.actor` 判断不能省。公开仓库里任何人都能评论，没有这一层，陌生人发一条 @claude 就能消耗你的 Token，甚至通过精心构造的 Issue 内容诱导 Agent 做出意料之外的修改。团队场景下，可以改为校验 `author_association` 是否为 OWNER、MEMBER 或 COLLABORATOR。
- **权限按需声明。** `permissions` 只给写内容、写 PR、写 Issue 评论的权限；`id-token: write` 用于 Action 通过 OIDC 换取 GitHub App 令牌，避免在仓库里存放长期有效的 PAT。
- **API Key 和 Base URL 都放在 Secrets 中。** Base URL 可选，用于接入企业网关或代理。网关层可以统一做限流、审计和成本归集，这也是企业通道相比个人账号的另一层优势。

## 三、Next.js + Netlify 的落地经验

本站是 Next.js 14 的静态导出站点，文章以 `.mdx` 文件存放在 `src/content/posts/`，构建时由 `gray-matter` 解析 Frontmatter 后渲染。下面是几条在真实运行中总结出的经验。

### 1. 让「构建通过」成为 Agent 的硬性出口条件

AI 生成内容最常见的失败不是写得差，而是写得「几乎对」：Frontmatter 多了一个未定义字段、日期格式不一致、正文里出现了会被解析为 JSX 的尖括号或花括号。这类错误在 diff 里很难一眼看出，却会让生产构建直接失败。

我们的做法是在 `CLAUDE.md` 中强制要求 Agent 在提交前依次执行 `npm run lint` 和 `npm run build`，任何一步退出码非零都不允许提交。这相当于把 CI 的检查前移到 Agent 内部，让它在自己的执行环境里完成「写代码、跑测试、修错误」的循环，而不是把失败的 PR 丢给人。

### 2. 用已有内容做格式锚点

与其在规范里罗列所有字段，不如指定一篇「标准范文」让 Agent 先读。本站要求动笔前先读取一篇现有文章和语法指南，沿用其字段名、数据类型和日期格式。这比任何文字描述都准确，因为范文本身就是通过了构建的。

另一个容易忽略的细节是渲染器的能力边界。本站的正文渲染器是一个轻量的逐行解析器，支持标题、列表、引用、代码块和行内的加粗、代码、链接，但不支持表格等复杂语法。Agent 需要知道这一点，否则写出的内容能通过构建，在页面上却显示异常。规范里写清楚「能用什么」，比事后修复成本低得多。

### 3. Deploy Preview 是评审的主界面

Netlify 对每个 PR 自动构建预览环境，并把地址回写到 PR 的检查项中。对于文章类任务，评审者真正关心的是排版、段落节奏和阅读体验，这些在 diff 里看不出来。我们把「打开预览地址通读一遍」作为 Merge 前的必要步骤，diff 只用来确认没有改动文章以外的文件。

对代码类任务同样适用：前端改动在预览环境里点一遍，比读 200 行 JSX 更快发现问题。

### 4. 留意静态导出的配置陷阱

本站 `next.config.js` 中使用 `output: 'export'`，`netlify.toml` 的发布目录是 `out`。`netlify.toml` 里还有一条把所有路径重写到 `/index.html` 的规则，这是单页应用的常见写法，但对静态导出站点并不必要：每个页面都已生成独立的 HTML，这条规则只会让不存在的路径返回首页而不是 404，掩盖死链问题。类似这样的配置不会让构建失败，却会影响线上行为，适合在人工评审中重点关注。

### 5. 控制成本与失败面

- **按任务类型区分标签。** `ai-article` 和 `ai-fix` 对应不同的规范段落，Agent 读取的上下文更聚焦，Token 消耗更可预测。
- **限制可执行命令。** Claude Code Action 支持通过参数配置允许的工具，例如只放行 `npm run lint` 和 `npm run build`，避免 Agent 在 Runner 上执行任意命令。
- **一个 Issue 只做一件事。** 需求越聚焦，一次通过率越高。我们的经验是，把「写一篇文章并顺便调整首页布局」拆成两个 Issue，总耗时反而更短。

## 四、给技术管理者的几点判断

**这套流水线改变的是协作粒度。** 过去「改个文案」「补篇文档」「修个样式」这类小任务需要找人排期，现在写一个 Issue 就能在十几分钟后拿到可预览的 PR。真正被释放的是工程师在小任务之间切换上下文的成本。

**可控性来自边界，而不是来自模型能力。** 身份校验、最小权限、独立分支、构建门禁、人工 Merge，这五道边界让我们可以放心让 Agent 在无人值守的情况下运行。模型能力会持续提升，但这些边界在任何阶段都不应该省略。

**规范文档成了新的基础设施。** `CLAUDE.md` 这类文件的质量，直接决定了 Agent 产出的一次通过率。它应该像代码一样被评审、被迭代，由团队共同维护。

## 结语

把 AI 从同步助手变成异步协作者，技术上并不复杂：一个工作流文件、一份规范文档、一个支持预览部署的托管平台，再加上一条稳定的企业级调用通道。难点在于想清楚边界：哪些环节交给机器，哪些决策必须留给人。先从文档和内容类任务开始，把闭环跑通，再逐步扩展到代码修复和小功能开发，是风险最低的路径。
